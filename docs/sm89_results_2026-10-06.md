# sm_89 GPU validation and tuning: RTX 4080, 2026-10-06

Local validation of specs 2 to 5 on a real RTX 4080, and the resulting
`build_flags/sm_89.flags`. All pool runs used a local test pool on
127.0.0.1:3333; no real pool was contacted. Raw logs stayed on the test machine
(`bench\`, not committed).

## Environment

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 4080, 16 GB (16,376 MiB), max SM clock 3,105 MHz |
| Driver | 617.14 |
| CUDA | 13.4 (nvcc V13.4.59), MSVC VS 18 Build Tools |
| CPU | Intel Core i5-13600KF, 14 cores / 20 threads; 32 GB RAM |
| OS | Windows 11 Home 10.0.26200 |
| Power limit | 340 W (default), clocks not locked |
| Commit | `a5628ad` (main, all specs 1 to 6 merged) |
| Pipeline | auto picks 2 contexts; `--pipeline 3` is capped to 2 by free VRAM on 16 GB |

**Benchmark protocol:** `tari_c29_solver_sm_89.exe --count 2000`, auto
pipeline, 60 s warm-up, then 3 runs back to back; the result is the median
`graphs/s`. A change counts as a gain only if the median is at least 0.5% above
the baseline median and every run is above the baseline median. Stage times come
from separate `-DTRIM_STAGE_TIMING=1` builds (`--count 200 --pipeline 1`, mean of
graphs 11 to 200) and are never used for g/s.

## Phase 1: spec 5a recall gate (sparse graph reset)

`python tests\tari_c29_gpu_recall.py run --candidate bin\tari_c29_solver_sm_89.exe --reference bin\validation\tari_c29_solver_sm_89_reference.exe --arch sm_89 --parity-pipeline 2`

pipeline 2 vs pipeline 1 all identical; 110 proofs over 4,200 graphs, no errors.

## Phase 6: ntrims sweep (spec 3), with `-DSEEDA_CHECKPOINT=32`

`powershell -File tools\ntrims_sweep.ps1 -Arch sm_89` (TARI_ARCH_FLAGS set to
the C32 set). 2-core check: affinity mask 5 (logical CPUs 0 and 2, SMT on).

| ntrims | g/s median | g/s runs | edges p99 | edges max | search ms p99 (full / 2-core) | busy full | busy 2-core (measured / projected) | result |
|---|---|---|---|---|---|---|---|---|
| 50 | 13.878 | 13.881 13.872 13.878 | 791,462 | 803,598 | 38.244 / 34.790 | 41.8% | 14.8% / 40.2% | stop: max edges > 524,288; projected busy 0.402 > 0.40 |
| 48 to 32 | | | | | | | | not run (stopped above) |

`chosen_ntrims=none`: the default 50 already exceeds both stop limits on this
machine, so no lower value was tried and no ntrims recall was needed. The
sweep's `sweep.md` reports `CUDA unknown (nvcc 13.4)`; the CUDA version line
is not parsed on this toolkit.

The stop reason lists OOPS / NODE OVERFLOW whenever either counter is non-zero
over the runs at that `ntrims`. It doesn't list them here, so no edges were
dropped at 50 trims. The worst graph used 76.6% of `MAXEDGES` (1,048,576),
leaving about 23% headroom, which the recall comparison can't check because the
reference runs the same 50 trims. `docs/ntrims_sweep.md` ("Measured: sm_89 at
the default 50 trims") covers what this means for spec 3 and the follow-up
(trying `ntrims` above 50 for weak hosts).

*Fixed after this run:* the sweep scripts now report the nvcc toolkit version
first and match the driver's CUDA version line more loosely, so this reads
`13.4 (nvcc ...)` instead of `unknown`.

## Phase 7: final set

`build_flags/sm_89.flags`: `-DSEEDA_CHECKPOINT=32`. Rebuilt with
`TARI_ARCH_FLAGS` unset; solver and pool miner both print
`Arch flags for sm_89 [build_flags\sm_89.flags]: -DSEEDA_CHECKPOINT=32`.

**Final recall** (file-based build, `TARI_ARCH_FLAGS` unset, no
`--candidate-ntrims`, ntrims 50 on both sides): **PASS**, 110 proofs over
4,200 graphs, all four comparisons identical, no errors.

The first attempt (2026-10-06) failed only on the harness's 1,800 s run
timeout. The PC went to sleep during the pipeline 2 parity run, which then
reported 1.423 g/s over 2,951 s of wall time. Its output was complete
(4,200 graphs, 110 cycles, `verify failures: 0`), and `compare` showed it
identical to pipeline 1 and to the reference. The full recall was re-run with
the PC kept awake and passed (above).

**Final benchmark**, back to back:

## Not covered here

- sm_86 (RTX 30) needs an RTX 30 card; `build_flags/sm_86.flags` is unchanged.
- `build_flags/sm_120.flags` is unchanged.
- The ntrims stop limits (50% of `MAXEDGES`, 2-core busy 0.40) are already
  exceeded at ntrims 50 on this build, so the sweep cannot try lower values.
  Whether those limits fit a single-GPU host like this one is a follow-up, as
  is testing `ntrims` above 50 on a weak host (see `docs/ntrims_sweep.md`).
- `TRIM_CUDA_GRAPH` (2b) lost 17%; `docs/spec2_gpu_validation.md` now warns
  against enabling it without a per-arch benchmark.
- Pipeline 3 could not be exercised on a 16 GB card (VRAM caps it at 2).
